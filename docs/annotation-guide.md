# Annotation guide

How to write `groundtruth/<suite>/<entry>.yaml` for a program. The schema is the Go type in `internal/groundtruth`; the matching and attribution rules are in [METHODOLOGY.md](../METHODOLOGY.md). This guide decides what goes into the file.

## What is an asset

An asset is one call in the program's source that performs a cryptographic operation or creates a cryptographic object bound to an algorithm, protocol, certificate or key, or one expression that creates related crypto material (an IV, nonce, salt, tag, shared secret, seed or generated private key; see [Related crypto material](#related-crypto-material)). Annotate the call, not the import, the type annotation or the variable.

These calls are assets:

- creating a cipher, hash, MAC, signer, KDF or key-agreement object that names its algorithm or fixes it by default (`AESGCM(key)`, `hashlib.sha256()`, `hmac.new(key, msg, "sha256")`, `PasswordHasher()` for Argon2id, `CryptContext(schemes=["bcrypt"])`, `argon2.using(type="ID")`);
- a one-shot operation that names its algorithm (`bcrypt.hashpw(...)`, `jwt.encode(..., algorithm="HS256")`, `private_key.sign(data, ec.ECDSA(hashes.SHA256()))`);
- a sign, verify, encrypt or decrypt call on a key, or a one-shot verify or decrypt function, each as its own asset, even on the same key. When the call does not name the algorithm, it takes the algorithm the program uses there (the key's type, or the token the program produced), with only the parameters its API fixes;
- computing a digest that the program passes on, such as pycryptodome's `SHA256.new(message)` handed to a signer, or a certificate fingerprint `cert.digest("sha256")`. A property that computes a digest counts as a call (paramiko `key.fingerprint`);
- generating a key or key pair (`rsa.generate_private_key(...)`, `Ed25519PrivateKey.generate()`, `AESGCM.generate_key(bit_length=256)`). A generation that hands the program a private key is also a piece of related crypto material, by the rule in [Related crypto material](#related-crypto-material);
- drawing bytes from a cryptographic random generator (`os.urandom(12)`, `secrets.token_bytes(32)`, `get_random_bytes(16)`), wherever it appears;
- creating a TLS context or an SSH transport (`ssl.create_default_context()`, `SSL.Context(SSL.TLS_METHOD)`, `paramiko.Transport(sock)`);
- parsing a certificate or a key from bytes, a file or PEM, or serializing one to them (`x509.load_pem_x509_certificate(...)`, `cert.public_bytes(...)`, `serialization.load_pem_private_key(...)`, `key.private_bytes(...)`, `key.to_pem()`), and building a certificate (the whole `CertificateBuilder()...sign(...)` chain is one asset);
- creating an IV, nonce, salt, AEAD tag, shared secret, seed or private key that the program uses, by the rules in [Related crypto material](#related-crypto-material).

These are not assets:

- imports, class names, type hints and constants;
- follow-up calls on an object whose creating call is already an asset: `update`, `digest`, `finalize`, `encrypt` and `decrypt` on a cipher object, `hexdigest`. A method on an object the program created is a follow-up (argon2-cffi `PasswordHasher().verify`, passlib `CryptContext(...).verify`); a function on a module or a library class is a one-shot call (passlib `argon2.verify`, `rsa.verify`). A call that performs a key agreement with the private key an object holds is an operation on a key, not a follow-up (`private_key.exchange(peer)`, ecdsa `ECDH().generate_sharedsecret_bytes()`). Exception: when creating the object performs one operation and a later call performs a different one (PyNaCl `Box(sk, pk)` agrees a key; `box.encrypt` then encrypts with XSalsa20-Poly1305), annotate both. A Fernet object's `decrypt` is its own asset too (owner decision 2026-11-05), as decrypt is for RSA-OAEP and AES; its `encrypt` stays a follow-up on `Fernet(key)`;
- an algorithm specification object that computes nothing (`hashes.SHA256()` inside `ec.ECDSA(...)`, `padding.OAEP(...)` or `padding.PSS(...)` even when assigned to a variable first, `PBKDF2HMAC(algorithm=...)`). It is a parameter of the asset that uses it and is named in that asset's `algorithm`;
- padding helpers (`padding.PKCS7(128).padder()`, `pad(...)`), constant-time comparisons (`hmac.compare_digest`), and calls that configure or attach to an existing context (`set_cipher_list`, `minimum_version = ...`, `use_certificate(cert)`, `load_received_public_key(key)`, `add_server_key(key)`, `connect(...)` on an SSH transport), and patching the standard library (`truststore.inject_into_ssl()`), because the contexts they affect are annotated where they are created;
- encoding and decoding that is not cryptographic (Base64, hex, PEM armoring on its own);
- the value a digest, MAC or signature computes (`digest.finalize()`, `h.hexdigest()`, `hmac.new(...).digest()`, what `sign(...)` returns). It is the output of an asset, not an asset or related crypto material of its own, even when the program names the variable `tag`: a digest, a MAC (HMAC included) and a signature produce no `digest`, `tag` or `signature` material, for any tool.

One asset per call and algorithm. Two calls on one line are two assets. A call that performs two algorithms named in its arguments, such as a JWE with `alg` `RSA-OAEP-256` and `enc` `A256GCM`, is two assets with the same lines. A call nested inside another asset's call is part of that asset unless it is an asset kind of its own (a random draw or a key generation nested in an encrypt call is still its own asset).

## Related crypto material

An initialization vector, nonce, salt, AEAD authentication tag, shared secret, seed or generated private key that the program uses is an asset with `asset_type: related-crypto-material` and a `material_type` from CycloneDX 1.7 `relatedCryptoMaterialProperties.type`: `initialization-vector`, `nonce`, `salt`, `tag`, `shared-secret`, `seed` or `private-key`. Annotate the expression that creates the value, once, where it is created. Passing it to a call (`modes.CBC(iv)`, `AES.new(key, AES.MODE_CBC, iv=iv)`) or reading it back (`cipher.iv`) is not another asset.

- **Material type.** The role the program gives the value, named by the parameter it is passed as: `modes.CBC(iv)` and pycryptodome `iv=` take an `initialization-vector`; `AESGCM.encrypt(nonce, ...)`, `ChaCha20Poly1305.encrypt(nonce, ...)` and pycryptodome `nonce=` a `nonce`; the salt argument of a KDF or password hash (`salt=`, `bcrypt.hashpw`'s second argument) a `salt`.
- **A random draw.** A draw that creates the material is two assets with the same lines: the `drbg` algorithm asset for the draw, and the related-crypto-material asset for what the draw becomes. `iv = os.urandom(16)` passed to `modes.CBC(iv)`, `nonce = os.urandom(12)` passed to `AESGCM.encrypt` and `salt = get_random_bytes(16)` passed to `PBKDF2` are each a draw and a piece of material. `bcrypt.gensalt()` nested in `bcrypt.hashpw(...)` is a salt at the `gensalt` call. It counts although the salt ends up in the hash string, because the program creates it and passes it on; only a salt the library draws for itself stays inside its output (below). A literal that creates the material (`salt = b"fixed"`) is the creating expression too, with no draw.
- **Made by a library call.** When a library call creates the material and gives it to the program as a value of its own, the asset is that call. pycryptodome `AES.new(key, AES.MODE_CBC)` without `iv` draws an IV that the program reads back as `cipher.iv`, and `AES.new(key, AES.MODE_GCM)` or `ChaCha20_Poly1305.new(key=key)` without `nonce` draws a nonce read back as `cipher.nonce`. The asset is the `new(...)` call, on the lines of the call, so that call is two assets with the same lines: its algorithm asset and the material. The material type comes from the parameter the program later passes the value back as (`iv=` makes an IV, `nonce=` a nonce), or else from what the library calls it.
- **Tag.** An AEAD authentication tag that a call returns separately from the ciphertext: pycryptodome `ciphertext, tag = cipher.encrypt_and_digest(data)`, cryptography `encryptor.tag`. The asset is the call that returns it, even when that call is a follow-up on a cipher object. A tag appended to the ciphertext (cryptography `AESGCM.encrypt`, PyNaCl `SecretBox.encrypt`) is not a separate value and not an asset. A MAC's output is a digest output, not a tag.
- **Shared secret.** The output of a key agreement: `private_key.exchange(peer)`, ecdsa `ECDH().generate_sharedsecret_bytes()`. The same call is also its `key-agree` algorithm asset.
- **Seed.** A seed counts when the program passes it to a crypto operation as its seed, such as the seed of a deterministic key generation or a DRBG.
- **Private key.** A key generation that returns a private key, alone or in a key pair, is two assets with the same lines: its `algorithm` asset (above) and a `related-crypto-material` asset with `material_type: private-key`. This holds for every asymmetric key generation, whatever shape the returned value has: `rsa.generate_private_key(...)`, `Ed25519PrivateKey.generate()`, `rsa.newkeys(2048)`, JCA `generateKeyPair()`, `generateKeyPairSync('rsa', ...)`, a JWK generator, `mlkem.GenerateKey768()` (the decapsulation key), ring `generate_pkcs8` and `EphemeralPrivateKey::generate`. The material takes the lines of the call that returns the key, never the anchor of the algorithm asset: with JCA it is the `generateKeyPair()` call, not `KeyPairGenerator.getInstance`. A key generation nested in another call (`add_server_key(paramiko.RSAKey.generate(...))`, `new JcaPGPKeyPair(..., gen.generateKeyPair(), ...)`) still has its material. The owner decided this on 2026-11-08: CycloneDX 1.7 models a private key as related crypto material (`relatedCryptoMaterialProperties.type` `private-key`), and an inventory of crypto assets is expected to list the private keys a program generates, since they are what needs protecting, rotating and replacing. It applies to every tool alike: a tool that reports the key generation only as an algorithm asset misses the material, and one that reports only the material misses the algorithm asset.

These are not related crypto material:

- material a library creates and keeps inside its own output or object, which the program never handles as a value: the nonce in a PyNaCl `EncryptedMessage`, the IV in a Fernet token, a JWE's IV and content key, the salt in a password hash string (argon2-cffi `PasswordHasher().hash`, passlib `.hash`, PyNaCl `argon2id.str`), the shared key a PyNaCl `Box` holds, ECDSA's per-signature nonce and PSS's salt;
- keys other than a generated private key. Generating a secret (symmetric) key (`AESGCM.generate_key()`, `KeyGenerator.generateKey()`, `OctKey.generate_key(256)`), or drawing random bytes the program uses as a key (`key = os.urandom(32)`, `secrets.token_bytes(32)` passed as an HMAC key, `pyotp.random_base32()`), stays a key generation or a `drbg` draw as described above. A call that generates a key pair inside an object and returns only its public key (Node `ecdh.generateKeys()`, python-ecdsa `ECDH().generate_private_key()`) keeps the private key inside the library's object, as above, so it has no material. Building a key from a seed or from bytes (`new EdDSAPrivateKeySpec(seed, curve)`, `SigningKey::from_bytes(...)`, noble-curves `keygen(seed)`, node-forge `ed25519.generateKeyPair({ seed })`) is not a generation. A key generated inside a key store that never hands the private key to the program (a JCA `KeyPairGenerator` of the `AndroidKeyStore` provider) has no material either. Parsing or serializing a key stays a `related-crypto-material` asset with no `material_type`;
- a value created outside the entry's files (a function parameter whose caller is elsewhere), and a constant `None` (`HKDF(salt=None)`). A value created in the entry and passed through a helper function (`salt = os.urandom(16)` then `kdf(salt)`) is annotated where it is created;
- additional authenticated data, plaintexts, ciphertexts, passwords and tokens. CycloneDX names them, but this benchmark does not annotate them.

## Lines

`lines` is `[start, end]`, the first and last line of the call expression, 1-based and inclusive. For a call split over several lines, the range covers the whole call, from the line with the callee name to the line with the closing parenthesis. Do not include the assignment target's line when it differs, decorators, or comments. Related crypto material takes the lines of the expression that creates it: `os.urandom(12)` assigned as a nonce, `get_random_bytes(16)` used as an IV, or the library call that draws it. The score matches a finding only when its lines overlap this range ([METHODOLOGY.md](../METHODOLOGY.md#matching-rules), `LINE_TOLERANCE = 0`), so a range that stops short of the closing parenthesis turns a correct finding on the last line into an FP. An `algorithm` asset may add the call that names its algorithm as an [anchor](#anchors).

## Anchors

`anchors` is an optional list of extra line ranges, `[[start, end], ...]`, on an `algorithm` asset whose operation and whose algorithm are written on different calls of one object. `lines` stays the call that performs the operation. An anchor is the call that names the algorithm for the same object in the same function. The score matches a prediction that overlaps `lines` or any anchor, and one prediction still takes at most one asset ([METHODOLOGY.md](../METHODOLOGY.md#matching-rules)). The owner decided this on 2026-11-05: crypto-finder reports a finding on the call that names the algorithm and derives the lifecycle calls around it from the call graph, and sonar-cryptography reports a crypto object where it is created, so both put a correct finding on the naming call.

These are the anchors, and nothing else is:

- **Key generation.** With `generateKey()` or `generateKeyPair()` in `lines`: the call that creates the generator and names its algorithm, `KeyGenerator.getInstance("AES")`, `KeyPairGenerator.getInstance("EC")`, a Bouncy Castle or net.i2p generator constructor (`new RSAKeyPairGenerator()`, `new Ed25519KeyPairGenerator()`, `new KeyPairGenerator()`), or Go's `curve := ecdh.X25519()` before `curve.GenerateKey(...)`; and `initialize(new ECGenParameterSpec("secp256r1"))` on the same generator, because it names the curve. `init(256)` and `initialize(3072)` state only a size and are not anchors.
- **JWT, JWS and JWE.** With the call that signs, encrypts, serializes or verifies in `lines` (`token.SignedString(key)`, `jwsObject.sign(signer)`, `jwe.encrypt(encrypter)`, `jws.getCompactSerialization()`, `received.verifySignature()`, `received.getPlaintextString()`, `jwtConsumer.processToClaims(jwt)`): `jwt.NewWithClaims(jwt.SigningMethodHS256, ...)` that creates the token, the `new JWSHeader(...)`, `new JWEHeader(...)` or `JWSHeader.Builder(...)` given to the object, and the jose4j setters on the object that name an algorithm (`setAlgorithmHeaderValue`, `setEncryptionMethodHeaderParameter`, `setAlgorithmConstraints`, `setContentEncryptionAlgorithmConstraints`, `setJwsAlgorithmConstraints`). A JWE header that names a key management and a content encryption algorithm anchors both of the call's assets; a jose4j setter anchors the one asset whose algorithm it names.
- **Random draws.** With the draw in `lines` (`random.nextBytes(iv)`, `random.generateSeed(16)`, `rng.fill(&mut salt)`, `ring::rand::generate(&rng)`, `generator.generateKey()` on a Spring `BytesKeyGenerator`): the call that creates the generator, `new SecureRandom()`, `SecureRandom.getInstanceStrong()`, `SystemRandom::new()` or `KeyGenerators.secureRandom(16)`, when the draw is made on that object in the same function. The anchor goes on the `drbg` asset only, never on the related crypto material the draw becomes.
- **An object that names its algorithm when created and works later.** ring `UnparsedPublicKey::new(&signature::ED25519, ...)` before its `verify(...)`, and node-forge `forge.hmac.create()` before `hmac.start('sha256', key)`.

Not an anchor:

- a call on another object: the RNG handed to a key generation (`EphemeralPrivateKey::generate(&X25519, &rng)` is not anchored at `SystemRandom::new()`), the peer's `UnparsedPublicKey::new(&X25519, ...)` in a key agreement, which acts on the program's own private key, or `new PBEKeySpec(...)` before `SecretKeyFactory.getInstance`;
- an algorithm specification object or a literal passed as an argument (`padding.OAEP(...)` assigned before `encrypt`, a list of algorithm names, a WebCrypto algorithm dictionary); they stay parameters of the asset, as above;
- a call that is an asset of its own (`createECDH('prime256v1')`), a call in another function, a protocol, certificate or related-crypto-material asset's neighbour (`new JSch()` before `getSession`), and any other neighbouring line.

Several assets may share one anchor: two draws on one `SecureRandom`, two key pairs from one generator. A prediction on that anchor still matches only one of them. Write each anchor as the lines of the naming call, by the rules in [Lines](#lines); `cbench validate` refuses an anchor that overlaps `lines` or another anchor of the asset, and an anchor on an asset that is not an `algorithm`.

## Fields

- `asset_type`: `algorithm` for operations and key generation, `protocol` for TLS and SSH contexts and sessions, `certificate` for parsing, serializing or building a certificate, `related-crypto-material` for parsing or serializing a key, for the private key a key generation returns and for the material in [Related crypto material](#related-crypto-material).
- `material_type` (related crypto material only): `initialization-vector`, `nonce`, `salt`, `tag`, `shared-secret`, `seed` or `private-key`, by the rules in [Related crypto material](#related-crypto-material). Parsing or serializing a key leaves it out.
- `primitive` (algorithm assets only): `ae` for authenticated encryption (AES-GCM, ChaCha20-Poly1305, XSalsa20-Poly1305, Fernet), `block-cipher` for a block cipher in a non-AEAD mode, `stream-cipher`, `hash`, `mac`, `signature`, `pke` for public-key encryption, `kdf` for key derivation and password hashing, `key-agree`, `drbg` for random generation. Key generation takes the primitive the program uses the key for, and none when the program only stores or serializes the key.
- `algorithm`: the specific algorithm, written as in the `internal/algo` table: `SHA-256`, `AES`, `ChaCha20-Poly1305`, `RSA`, `RSA-OAEP`, `RSA-PSS`, `ECDSA`, `Ed25519`, `X25519`, `HMAC`, `PBKDF2`, `scrypt`, `bcrypt`, `Argon2id`. Never a family (`SHA-2`, `AES` with no further detail is fine because AES is the algorithm). A signature or MAC whose usual name carries its digest is written split, the scheme in `algorithm` and the digest in `parameters.hash`: `HMAC` with hash `SHA-256`, not `HMAC-SHA-256`; JCA `SHA256withRSA` is `RSA` with padding `PKCS1v15` and hash `SHA-256`. A JWS algorithm is named by what it computes: `HS256` is `HMAC` with hash `SHA-256`, `RS256` is `RSA` with padding `PKCS1v15` and hash `SHA-256`, `PS256` is `RSA-PSS` with hash `SHA-256`, `ES256` is `ECDSA` with curve `P-256` and hash `SHA-256`, `EdDSA` with an Ed25519 key is `Ed25519`. An algorithm missing from the table keeps its usual name (`XSalsa20-Poly1305`, `Fernet`, `SHA-512-crypt`). A random draw from the operating system generator has no algorithm. A generic EC key (`ec.generate_private_key`, `ECC.generate`, `ECKey.generate_key`, `generate_pair("ec", ...)`) is `EC` with its curve; a key type tied to one scheme is named by the scheme (`ecdsa.SigningKey` is `ECDSA`, `Ed25519PrivateKey` is `Ed25519`, `X25519PrivateKey` and PyNaCl `PrivateKey` are `X25519`). A generic secret key (`OctKey.generate_key`) has no algorithm. Protocol, certificate and related-crypto-material assets have no algorithm.
- `parameters`: only what the call itself states, as a literal argument or a variable assigned a literal in the same function, or what its API fixes (`rsa.encrypt` and `RS256` are always PKCS#1 v1.5, `aes_cbc_pkcs7_encrypt` always CBC with PKCS7): `key_size` in bits (the key of the cipher, MAC or key pair; a KDF's output length and a cost factor are not a key size), `mode` (`GCM`, `CBC`, ...), `curve` (`P-256`, `secp256k1`), `padding` (`PKCS1v15`, `PKCS7`; OAEP and PSS are named by the algorithm instead), `hash` (below). Do not carry a key size from the line that generated the key to a later call that uses it. Leave out a parameter the algorithm admits only one value of: ChaCha20-Poly1305 and XSalsa20-Poly1305 keys are always 256 bits, so they carry no `key_size`.
- `hash`: the digest a signature or MAC computes (`SHA-256`, `SHA-1`), on signature and MAC operations only. Set it when the asset's call names the digest (`hmac.new(key, msg, hashlib.sha256)`, `ec.ECDSA(hashes.SHA256())`, `rsa.sign(msg, key, "SHA-256")`, `algorithms=["RS256"]`), when the call or a follow-up call on the object it creates receives a digest object the program computes in the same function (pycryptodome `pss.new(key).sign(h)` after `h = SHA256.new(message)`, and `verifier = DSS.new(...)` then `verifier.verify(SHA256.new(message), signature)`), or when its API fixes it (`HS256`, `RS256`, pyotp's default SHA-1). Do not carry a digest bound to a key when the key was created or loaded to a later sign or verify call on that key (python-ecdsa `SigningKey.generate(..., hashfunc=sha256)` then `sk.sign(message)`), just as a key size is not carried. A call that names no algorithm and takes it from the token (rule above) gets no `hash`. Key generation, KDFs, password hashes and RSA-OAEP get no `hash`, even when the usual name carries a digest (`RSA-OAEP-SHA256`, `PBKDF2-HMAC-SHA256`): write `RSA-OAEP` and `PBKDF2`. The methodology splits that digest off a tool's name so the names match, and a tool may report the digest as a parameter the ground truth does not set.
- `origin: project`, `reachable: true` and `depth: 0` for suite A programs, whose crypto runs from `main`.
- `object`: the id shared by the assets that act on one crypto object, by the rules in [Objects](#objects). Leave it out when the asset is its own object.
- `notes`: anything a second annotator might decide differently, and how a disagreement was resolved.

`scope.kind: exhaustive` means every asset in every file of the entry is listed. A missing asset is a ground-truth error that turns a correct tool finding into a false positive.

## Objects

The `object` field groups the assets that act on one crypto object, for the object-level view of the score ([METHODOLOGY.md](../METHODOLOGY.md#object-level-view)). Some tools report a crypto object once, where it is created, and not each operation on it. The object view scores every tool on the objects it finds.

An object is a key or a key pair, together with the crypto objects the program builds on it. Its assets are the call that creates the key, every object built on the key, and every operation the key performs: sign, verify, encrypt, decrypt, key agreement, a MAC, or a JWS, JWT or JWE call given the key. Give these assets one `object` id that no other object in the entry uses. Write it as `<program directory>/<variable>`, such as `rsa-oaep/private_key`. When one key has an `algorithm` object and a `related-crypto-material` object, the first takes the key's variable and the second the variable of its first serialization (`key-load/pem`). An object with no variable of its own takes the variable that carries it. The score compares ids only for equality within an entry, so their spelling never changes a result.

- **Key pair.** A private key and its public key are one object. `private_key.public_key()`, python-ecdsa `sk.verifying_key`, PyNaCl `signing_key.verify_key` and `bob.public_key` belong to the key they come from, and serializing the public key belongs with the serializations of the private key.
- **Built on a key.** A cipher, MAC, signer or key-agreement object created from a key, or one that creates the key itself, joins the key's object: `AESGCM.generate_key()` then `AESGCM(key)`, `Fernet.generate_key()` then `Fernet(key)`, `DSS.new(key, ...)`, python-ecdsa `ECDH(curve=...)` and the key its `generate_private_key()` makes. Two objects built on the same key are one object, and so are two one-shot calls given the same key: `hmac.new(key, ...)` twice, `AES.new(key, ...)` for encryption and again for decryption, `jwt.encode(..., key)` then `jwt.decode(..., key)`.
- **Passed on.** A key stays the same object when the program serializes it and passes the bytes on, writes it to a file and reads it back, or passes it inside a library's output. Parsing those bytes (`load_pem_private_key(pem)` of a `pem` the program serialized from the key), every operation on the parsed key, and a JWT call given the PEM act on the same key. A JWE's content key goes from `encrypt` to `decrypt` inside the token, so the content-encryption assets of the two calls are one object, apart from the key that wraps the content key. A certificate the program builds, serializes and parses again is one object in the same way.
- **Derived keys.** A key agreement acts on the private key that performs it: `alice.exchange(bob.public_key())` is alice's. A key that a key agreement or a KDF derives is a new object each time it is derived. The two PyNaCl `Box`es that two parties build are two objects, although they hold equal keys. The key agreement of `Box(alice, bob.public_key)` is alice's, and the XSalsa20-Poly1305 the box then runs belongs to the box's derived key, not to alice. The AES-GCM and the scrypt that pycryptodome `export_key(protection="scryptAndAES256-GCM")` runs belong to neither the exported key nor the passphrase.
- **One asset type.** An object groups assets of one `asset_type`. Generating a key (`algorithm`) and serializing it (`related-crypto-material`) are two objects, and so are a key and the certificate it signs. The serializations and parses of one key are one `related-crypto-material` object.

Leave `object` out, so that the asset is its own object, for:

- a random draw, even when the program uses its bytes as a key (`key = os.urandom(32)`). The calls given that key still share an object when there are two or more of them. So `key = os.urandom(32)` and one cipher on it give no object, while `AESGCM.generate_key()` and `AESGCM(key)` give one: a draw is an asset kind of its own, and a cipher's key generation is not;
- related crypto material with a `material_type`: each value is its own object;
- a one-shot call given no key: a hash (`hashlib.sha256(data)`, `SHA256.new(message)` handed to a signer), a password hash or its verify (`bcrypt.hashpw`, `bcrypt.checkpw`, passlib `.hash` and `.verify`), a KDF given a password and a salt (`hashlib.pbkdf2_hmac`, `bcrypt.kdf`). A password is never a key here, so two KDF calls given the same password are two objects;
- a digest of a key or a certificate (paramiko `key.fingerprint`, pyOpenSSL `cert.digest("sha256")`). The key does not perform the hash;
- a TLS context or an SSH transport. Each is its own object, even when two of them connect to each other;
- an object that has only one asset.

`cbench validate` refuses an `object` id that only one asset uses, an object whose assets have different asset types, and an `object` on an asset that has a `material_type`.

## Suite B

A suite B pair is two entries, a `reachable` and an `unreachable` variant of one scenario, that share their libraries and differ in one change to the application ([fixtures/README-suite-b.md](../fixtures/README-suite-b.md)). The manifest names the scenario in `scenario`, the same on both entries. Every asset of a pair entry is annotated in both variants, in the libraries as well as in the application, with these fields on top of the ones above:

- `origin: dependency` and `component`, the package URL the library is installed under (`pkg:golang/example.com/cbench/transitive/libb@v1.0.0`, `pkg:pypi/cbench-transitive-libb@1.0.0`, `pkg:maven/org.cbench.transitive/libb@1.0.0`, `pkg:npm/cbench-transitive-libb@1.0.0`, `pkg:cargo/cbench-transitive-libb@1.0.0`).
- `file` relative to the component's root: the Go module root (`libb.go`), the root of the installed distribution, which is where the wheel's `RECORD` names its files (`libb/codec.py`), the root of the Maven sources jar (`org/cbench/transitive/libb/Digests.java`), the npm package root (`index.js`), the crate root (`src/lib.rs`).
- `reachable`: `true` when the application's entry point runs the asset on some path, `false` otherwise. Never `unknown` in a pair. The entry points are Go's and Rust's `main`, Java's `public static void main`, the function Python's `if __name__ == "__main__":` guard calls, and the function JavaScript's top-level code calls. An application function that the entry point never calls is not an entry point, even when nothing calls it and it is public. A function the entry point hands to a framework or a library function that calls it is reached through that call: a request handler it registers, by reference or by an annotation on a class the framework then creates (a Spring `@RestController`), or a function value it passes as a callback (`slices.SortFunc`, `threading.Thread(target=...)`). The same function is not reached when the entry point never hands it over and nothing calls it. An interface, trait or method call reaches only the implementation of the object that path actually creates.
- `depth` and `distance`. `distance` is the number of dependencies on the chain from the application to the component, where each one imports the next: 1 for a library the application declares and imports, 2 for that library's own dependency, 3 one further. `depth` is `distance` capped at 2. In Go, a `// indirect` requirement in a library's `go.mod` is not a link of the chain, because the library does not import it.
- `path`: the call path from the entry point to the function that holds the asset, one function per item, only when `reachable` is `true`. It documents the ground truth; the score does not compare it.
- `scope.components`: the fixture libraries. A library that calls a third-party crypto crate (Rust's `sha2` and `hmac`) or an environment that holds other packages (`pip` in the virtual environment) gives findings in components the ground truth does not annotate; `scope.components` leaves them out of the score.

`cbench validate` refuses a pair entry without a scenario, and a pair asset with `reachable: unknown`, without `distance`, with `reachable: true` and no `path`, or with `reachable: false` and a `path`.

## Process

Annotators are agents; there is no human annotator. Two annotators label each entry independently from the program files and this guide. One may be the author of the programs; the other is a fresh agent that sees only the program files, this guide, the schema and the `internal/algo` tables, never the first annotation. The two lists are diffed, every disagreement is resolved by reading the code against this guide, and the resolution goes into the asset's `notes`. Agreement counts per entry are recorded in [annotation-log.md](annotation-log.md).
